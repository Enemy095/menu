# INF-002 - Windows Docker application launcher

## Objective and scope

Provide a single Windows entry point for local Docker Desktop startup, cached
application builds and health-checked full-stack startup. Keep the approved
Next.js / Java 25 Spring MVC / PostgreSQL / S3-compatible stack.

Dependencies: INF-001. This does not perform production deployment, Git pulls,
dependency upgrades, content imports or destructive infrastructure resets.

## Ownership and deliverables

- `start-docker.cmd`, `scripts/start-docker.ps1`: Windows entry point and orchestration.
- `infra/docker/*.Dockerfile`, `.dockerignore`: isolated builds and non-root runtimes.
- `compose.yaml`, `.env.example`: opt-in application profile and local ports.
- `apps/web/next.config.ts`: Docker-only standalone output for the monorepo.
- `infra/local/README.md`: operator workflow, persistence and readiness semantics.

## Implementation and interfaces

1. Locate Docker CLI/Desktop and wait for a Linux engine with a bounded timeout.
2. Create missing `.env`; reuse existing local settings and optional Telegram env file.
3. Validate Compose without printing secrets; build before replacing containers.
4. Start PostgreSQL, MinIO/init, API/worker and Next.js; wait for health checks.
5. Print resolved public ports and exit nonzero on failure.

Compose keeps the existing project/volume names. Container-to-container URLs use
service DNS; browser URLs retain localhost. The frontend routes order requests
through its existing server handler. Business data and source contracts are unchanged.

## Acceptance and failure cases

- Run `start-docker.cmd` with Docker Desktop stopped and already running.
- Run it twice: unchanged build layers must use cache and healthy containers remain.
- Change a build input: Docker must invalidate the relevant layers.
- Fail a build: existing application containers must not be replaced.
- Missing CLI, Windows engine mode, invalid Compose and health timeout must fail clearly.
- PostgreSQL/MinIO volumes persist; empty DB frontend 404 is accepted as HTTP liveness.
- Docker build contexts exclude env files, host outputs and local agent metadata.
- Validate PowerShell 5.1 syntax, Compose config, frontend lint/build, API image build,
  readiness and `git diff --check`.

## Handoff

Verified on Windows / Windows PowerShell 5.1 on 2026-10-26:

- Docker application images built successfully: Java 25 `bootJar` and Next.js production build.
- Frontend lint, TypeScript check and runtime architecture guard passed.
- Compose config validated with app/assets and optional observability profiles.
- Root CMD launcher also succeeded when invoked from a different working directory.
- HTTP `/` returned 200; API readiness returned `UP`; existing menu returned 4 categories / 23 items.
- Final unchanged launch exited 0, reused 24 build steps and preserved all running container IDs.
- PowerShell syntax validation and `git diff --check` passed.

The installed Compose/containerd combination ignored the Compose provenance flag;
the launcher also scopes `BUILDX_NO_DEFAULT_ATTESTATIONS=1` to its build command.
This follows Docker's [default attestation control](https://docs.docker.com/build/metadata/attestations/).

Initial machine validation encountered inaccessible Docker Desktop IPC sockets.
Transient socket parent directories were preserved under timestamped backup names
outside the repository; the Desktop engine then started. No factory reset, volume
deletion or business-data import was performed. Repairing Docker Desktop itself is
not built into the project launcher.

This local tooling task does not change release acceptance or production cutover status.

Compatibility follow-up: removed `build.provenance` from Compose because Docker
Desktop's Compose 2.35.1 rejects the field before startup. The existing scoped
`BUILDX_NO_DEFAULT_ATTESTATIONS=1` build control remains. Validated the application,
assets and observability configuration with the official Compose v2.35.1 Windows
binary, as well as the installed Compose version.
